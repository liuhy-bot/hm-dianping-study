# 02 集群下的一人多单并发问题

## 现象

单机部署时「一人一单」逻辑是可靠的：用 `synchronized` 锁住 `userId` 字符串对象，
同一用户的并发下单会被串行化。

但两个实例一起跑之后，同一个用户在同一时刻下出了两张券。

## 复现方式

- 环境：nginx 8080 → 两个后端实例 8081 / 8082
- 券：`voucher_id = 10`，库存 100
- 方式：Python 20 个线程，用 `threading.Barrier` 让请求同时发出
- 接口：`POST /api/voucher-order/seckill/10`，Header 带登录 token

结果：**20 个请求，2 个成功，18 个返回「不能重复购买」**。

产生两个订单号：

```
660017915117961221
660017915117961222
```

数据库确认：

```sql
SELECT id, user_id, voucher_id FROM tb_voucher_order WHERE user_id = 5 AND voucher_id = 10;
-- 2 行

SELECT stock FROM tb_seckill_voucher WHERE voucher_id = 10;
-- 98（原 100，被扣了两次）
```

## 原因

锁的边界是 JVM，而不是业务。

```java
synchronized (userId.toString().intern()) {
    // 创建订单
}
```

`intern()` 保证相同字符串在**同一个 JVM 的字符串常量池**里是同一个对象，所以单机下这把锁有效。

但两个实例 = 两个 JVM = 两个独立的堆和常量池。
8081 上的锁对象和 8082 上的锁对象是两个毫不相干的内存地址，
8081 的线程持有锁时，8082 的线程根本不知道有人在等。

于是两个实例可能同时走到「查询订单数 → 判断是否下过单」这一步，
两边都查到 0，两边都扣库存、都插订单。

## 为什么正好是 2 条

这个数字本身能反证两件事：

1. **负载均衡确实在工作**：nginx 轮询把 20 个请求大致对半分给了两台
2. **单机锁确实有效**：每台内部的 10 个请求被串行化，只放过 1 个

每边各放行 1 个，总共 2 个。

对照：单实例跑同样的脚本结果是 1 条；如果锁完全不起作用，会接近 20 条。

## 结论

`synchronized` 只能保证单 JVM 内的互斥。方案要适用于集群，锁必须放在所有实例都能访问的地方，
也就是 JVM 之外，比如 Redis。

## 下一步

用 Redis 的 `SETNX` 实现分布式锁：

- key 形如 `lock:order:{userId}`，`SETNX` 成功即抢锁成功
- 必须设置过期时间，防止持有者崩溃后死锁
- 释放时先比对持有者标识，再用 Lua 脚本保证「判断 + 删除」的原子性
